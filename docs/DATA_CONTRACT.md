# TAKO-SEN — 問題・履歴データ契約

本書は API・同期実装が満たすべき契約を定める。第2段階として、非公開の完了履歴 API と開発用 D1 を導入した。ゲームルールの正本は [`DESIGN.md`](./DESIGN.md) とする。

## 問題の同一性と再現

- 表示用シードコード `TAKO:<generatorVersion>:<difficulty>:<seed>` は再生成の入力であり、問題IDではない。同じシードでも Generator の版が違えば別の入力となる。
- 問題ID `p1:<SHA-256 hex>` は UTF-8 の正規形 `JSON.stringify(["p1", generatorVersion, size, regions, sortedGivens])` から作る。`generatorVersion` がない旧ローカル盤面は `g1` とみなす。`givens` がない場合は空配列とする。`solution` と `seed` は問題IDへ含めない。
- 問題IDは盤面・公開初期配置の同一性を表す。選択難易度、実際の評価、表示色は含めない。ハッシュを作る前に盤面形状と解の一意性を検証する。
- 新規生成は `g2`。`g1` 生成器の挙動は `generator-g1.ts` に凍結し、3難易度・9入力の盤面全体ハッシュを固定テストで確認する。復元・共有作成・履歴の問題ID検証はコードの版で生成処理を振り分ける。版なし旧盤面はコード化でも `g1` と扱う。以後の版追加でも既存版を単に書き換えない。
- オンライン共有ではサーバーに盤面スナップショットと版を保存する。旧版コードは対応する版の生成器でローカル復元し、版を保持できなくなった場合も共有済み問題は保存済みスナップショットから開く。正解配置を公開 API で返さない。

## ローカル保存と版

- 現行キー `tako-sen.current-game.v2` と `tako-sen.results.v2` は別々に扱う。履歴は `version: 2` を持つ。v2がない場合だけv1を読み、最大ヒント段階を補ってv2へ保存する。旧キーは削除しない。v2が壊れている場合は旧v1へ勝手に巻き戻さない。旧盤面ではREADY・計時フィールドも省略され得る。
- 読み込み時は JSON の構造と値域を検証する。壊れた値はゲーム開始を妨げず、新規状態で起動する。破損値を上書きする前に退避し、後で調査・手動復旧できるようにする。
- 保存形式を変える場合は新しい版のキーを使い、読み込み時に旧版を移行する。移行成功前に旧データを削除しない。
- `playId` は試行開始時の UUID で、ローカル結果とサーバー送信の冪等キーにする。`userId` はローカル匿名IDであり、ログイン済みアカウントの認証情報ではない。

## 履歴の移行と同期

- ゲーム名・公開同意の設定後、ログイン中に新たにクリアした完了履歴を自動送信する。過去履歴の取り込みは廃止する。未ログイン・同意前の結果は後から送信しない。送信後もローカル履歴は削除しない。
- サーバーは認証済みアカウントIDと `playId` の組を一意に扱う。同じ内容の再送は成功として扱い、異なる内容の再送は上書きせず競合を返す。別アカウントへの同一ローカル履歴の自動移行はしない。
- 初期同期の対象は完了履歴のみとする。プレイ中の盤面は各端末に残し、別端末から自動上書きしない。将来の途中盤面同期は競合 UI を設計してから追加する。
- 未送信結果は `tako-sen.sync-outbox.v2`（`version: 2`）にアカウント ID と結果の組として保存する。v2がない場合だけ旧v1を移行し、旧キーは残す。送信は同一アカウントの認証セッションに限り、成功するまで保持する。再接続・再ログイン時と30秒間隔で再試行する。同意情報の端末キャッシュはオフライン時のキュー追加にのみ用い、サーバーの認証・同意判定に代用しない。保存失敗は画面で知らせ、破損キューは退避して自動送信しない。
- 退会時は Clerk アカウントとそのアカウントに紐づく D1 の履歴、ゲーム名・同意情報、初回ランキング記録、投稿制限の情報を削除する。公開ランキングにも残さない。退会操作した端末の未送信キュー・同意キャッシュも無効にする。端末のローカル履歴は削除しない。
- 完了日時・経過時間・ミス・ヒント数は履歴として受け取るが、クライアント申告値である。公開ランキングでは参考記録と明示し、サーバーで形式・値域・問題ID・所有者・重複を検証する。

## API 境界の要求

- 投稿で `userId` を認証根拠にしない。サーバーはセッションからアカウントIDを決める。
- 結果送信では `playId`、問題ID、シードコード、Generator版、開始・完了日時、経過時間、ミス数、ヒント数を検証する。クライアントから送られた解答セルや `solution` を信頼しない。
- 履歴の取得は本人のみ。公開ランキングはゲーム名の設定時に明示同意した本人の、新規登録された初回クリアだけを含める。
- API が利用できなくてもローカルの問題生成・プレイ・保存・ヒントは利用可能にする。

通常問題の候補取得 `GET /api/next-puzzle?difficulty=easy|normal|hard` はログイン済み本人だけが利用する。公開初回スコアがある盤面のうち、本人のオンライン完了履歴に同じ問題IDがない候補を、問題ID・シードコード・登録人数のみ最大30件返す。アカウントID・他者の成績や解答は返さない。クライアントは版付きシードから再生成して問題IDを照合し、取得不能時はローカルで生成する。

## 回帰テストにする境界条件

1. 同じ盤面・版・初期配置から同じ問題IDを得る。シード・解答順序・表示色では変わらない。
2. 盤面、公開初期配置、Generator版のいずれかが変わると問題IDが変わる。
3. 旧保存形式を読み込め、壊れた JSON・不正な値からもゲームを開始できる。
4. 同じ `playId` の再送では重複しない。異なる内容は黙って上書きしない。
5. 未ログイン・名前設定前の履歴は送信しない。別アカウントの未送信結果は送信しない。ログアウト後もローカルプレイはできる。
6. 2端末の途中盤面は初期同期で統合・上書きしない。
7. `g1` コードは将来版追加後も同じ盤面に復元できる。

認証基盤は Clerk とする。`GET /api/plays` は認証済み本人の直近500件の完了履歴を返し、`POST /api/plays` は1件を登録する。サーバーは Clerk セッションからアカウント ID を取得し、ローカル `userId` を認証根拠にしない。同一アカウント・同一 `playId` の同内容再送は成功、異なる内容は `409` とする。投稿時はシードから盤面を再生成し、問題IDを再計算する。API は開発用 Worker にデプロイ済みで、本番公開はしていない。

`DELETE /api/account` は認証済み本人の D1 履歴を削除してから Clerk アカウントを削除する。Clerk 側で直接削除された場合は、署名検証済み `user.deleted` webhook で D1 履歴を削除する。Webhook は非同期であり、設定と到達確認が済むまで公開運用は始めない。

問題共有の作成は認証済み本人のみ `POST /api/puzzles` にシードコードを送る。サーバー側でコードが指定する版の Generator から盤面を再生成して問題 ID を計算し、D1 に正解配置を含まない公開スナップショットを保存する。同じ問題 ID の再作成は既存スナップショットを維持する。`GET /api/puzzles/:id` は未ログインでもスナップショットを取得できる。受け取った側はスナップショットを検証し、Complete Solver で唯一解を復元してからゲームを開始する。生成器を将来更新しても、保存済みスナップショットの盤面自体は再生成に依存しない。共有作成の濫用対策・旧版スナップショットの結果送信は公開運用前に確認する。

公開スナップショットには作成者のアカウント ID とプレイ記録を保存しない。退会時も共有された盤面自体は残るが、作成者との紐付けはない。URL を知る人は盤面・シードを閲覧できるため、非公開情報をシードに含めない。

## 公開ランキングとプロフィール

- `GET /api/profile` は本人のゲーム名・同意版だけを返す。未設定なら `null`。Clerk の ID・氏名・メールをゲーム表示には使わない。
- `POST /api/profile` は `displayName` と `consentVersion: 1` を受け取る。書記素単位で2〜20文字の文字・数字・結合文字・絵文字・空白・ハイフン・下線を許可し、NFC 正規化と前後空白の除去を行う。国旗・肌色・ZWJ による組み合わせ絵文字を許可するが、単独の不可視制御文字や双方向制御文字は許可しない。名前は最大256 UTF-16コード単位、プロフィールのリクエストは最大4096バイトとする。本名・メールを使わないよう案内する。他アカウントとの名前重複は `409`。同意済みの登録の再送では名前・同意を変更しない。
- 名前設定時に、ログイン中のクリアの自動同期、初回成績の自動公開、個別非公開なし、退会による削除、第三者のコピーは回収できないことを説明し、チェックボックスで明示同意を得る。
- ログイン後にサーバーでプロフィール未設定と確認できた場合は、名前と公開同意だけの必須モーダルを自動表示し、保存まで閉じられないようにする。プロフィール取得に失敗しただけでは未設定と断定せず、ローカルプレイを妨げない。
- `POST /api/plays` はサーバーで同意済みプロフィールを要求し、未設定は `403 profile_required`。既存の結果検証・認証済み本人の所有権・`playId` の重複/競合判定を維持する。
- 初回はアカウント・問題 ID ごとの最初のサーバー登録とする。D1 の挿入トリガーと `first_ranked_plays` の複合主キーにより、履歴登録と初回の選択・公開を同一トランザクションで行う。同時送信でも1件だけが選ばれる。クリア日時が古い後着や再挑戦で置き換えない。再挑戦も個人履歴には保存する。
- 新規の同意済み履歴登録はアカウントごとに60秒の固定窓で10件まで。超過は `429` と `Retry-After: 60`。同内容の再送は制限しない。拒否した挿入とランキング反映はロールバックする。
- `GET /api/leaderboards/:puzzleId` は未認証でも利用可能。同一問題 ID の各参加者の初回成績を最大100人返す。[`DESIGN.md`](./DESIGN.md) 第19章のスコア降順、同点なら時間・ミス数・ヒント数の昇順で比較し、すべて同じ成績は同順位（1、1、3）。順位の境界に同点が多い場合も最大100人とする。
- 公開応答はゲーム名・順位・時間・ヒント数・最大ヒント段階・ミス数だけを含む。氏名・メール・Clerk ID・ローカル ID・試行 ID・日時は含めない。ゲーム名は公開されるため、個人情報を名前に含めないよう案内する。
- 記録単位・全件の公開取り消しは廃止する。旧 `PUT/DELETE /api/plays/:playId/publication` と `DELETE /api/publications` は `404`。退会と署名付き `user.deleted` webhook でゲーム名とすべてのランキング記録を削除する。
- `0004_automatic_ranking.sql` 適用で旧公開状態を非公開に戻す。既存履歴・旧自動生成名は同意済みとみなさず、既存履歴を新ランキングへ再公開しない。本人のオンライン履歴としては残る。
- 公開応答は `Cache-Control: no-store`。退会後、閲覧中の画面は再取得時に反映する。第三者の保存済みコピーまでは回収できない。
- 成績はクライアントの自己申告による参考記録であり、不正耐性のある競技順位ではない。一般公開前の監視・サービス全体の濫用対策は別途必要。

回帰テスト: 同意なしの送信拒否、既存履歴の非公開維持、再送の重複排除・競合、同時挿入で初回1件、初回より速い再挑戦と古い後着による非上書き、投稿制限とロールバック、同順位、別問題・別アカウント分離、ゲーム名の検証・重複、公開応答の識別子除外、退会・webhook 後の削除、オフライン再送と別アカウントへの誤送信防止。

## 最大ヒント段階の契約（2026-09-29）

- プレイ状態・完了記録・結果送信・本人履歴・公開ランキングに `maxHintStage` を追加する。未使用は0、通常ヒントは1〜3、矛盾調査は1〜4。表示した最大値を保持し、次のヒントや再表示で下げない。×の適用は通常ヒントの段階3に含める。
- APIでは整数0〜4または `null` を受け付ける。ヒント0回なのに正の段階、使用ありなのに段階0、負数・小数・範囲外・文字列などは拒否する。旧クライアントの省略はヒント0回なら0、使用ありなら `null` に正規化する。`null` は「段階不明」であり未使用とは扱わない。
- 旧盤面で過去にヒント使用ありの場合、再開後にヒントを見ても過去の最大値は断定できないため不明を維持する。旧履歴・未送信キューにも同じ補完方針を使い、旧データを削除せず、過去履歴を新たに自動送信しない。
- `0005_hint_stage.sql` はD1へnullableな `max_hint_stage` を追加し、既存のヒント0回だけ0へ補完する。初回スコアの選択・公開状態・同意・ゲーム名は変更しない。
- 同じ `playId` の再送判定には正規化した最大段階も含める。段階だけが違う再送も競合として扱い、既存記録を上書きしない。値は他の成績同様に自己申告であり、解法をサーバーで検証した証明ではない。
- 最大ヒント段階は表示・記録を続けるが、順位比較には使用しない。公開順位・ローカル順位・オンライン問題別自己ベストは [`DESIGN.md`](./DESIGN.md) 第19章のスコア基準を使う。初回スコアのみという公開ルールは維持する。
- 開発用リモート環境への反映時は、先にD1へ0005を適用してから新Workerと画面をデプロイする。追加列がない環境で新Workerを動かさない。現時点ではローカル確認用D1だけに適用済み。

## 超級の契約（2026-10-09 承認・実装中）

以下は承認済みの実装契約であり、API・DB・画面への接続が完了したことを示さない。

- シードは `TAKO:super-v1:hard:<URI encoded seed>`。seed は1〜128 UTF-16コード単位とし、日付に制限しない。`super-v1` は10×10・10 Region・10匹、追加する2つの1マスRegionにタコを公開し、唯一解・対応定石による上級評価を検証する。問題IDは既存の正規形に `super-v1` とサイズ10を含める。`g1`・`g2`・`daily-v1` と別モードとして復元する。通常コードのパーサーへ無条件に混ぜず、認証・オンライン確認済みの超級導線からのみ扱う。
- 通常8×8の試行で最初に盤面が変わった時、ログイン・名前と公開同意設定後なら対象イベントを作る。共有・復元・再挑戦も別の `playId` なら対象。デイリー・超級・練習・未操作・既存履歴は対象外。イベントは同意済みアカウントに紐付けて端末へ保存し、同じアカウントでのみ再送する。ローカル匿名IDで所有権を証明しない。
- サーバー正本の進行は `cycle`（権利消費ごとに増える世代）、`count`（0〜10）、`offerPending`（10回到達後の未案内）で表す。試行に開始時の世代を紐付け、対象イベントの `(account_id, play_id)` を重複排除し、その登録と加算を原子的に行う。権利保留中も対象イベントを処理済みとして記録し、権利消費後の再送や古い世代の後着で加算しない。通信断中は最後に確認した本人の世代を使い、未知の世代を捏造しない。
- 10回で1回分だけ保持し、保留中は加算せず、積み増し・繰り越し・過去履歴の換算は行わない。案内済み状態もサーバーへ保存して再読み込み・別端末で繰り返さない。未ログイン・同意前の操作は後からイベント化しない。
- 超級READYのOKでは、本人・同意・オンライン・端末保存成功を確認する。権利経由の開始は現在世代と権利を照合し、開始試行の登録と権利消費・世代更新を同一トランザクションで行う。同じ `(account_id, play_id)` の同内容の再送は成功、異なる内容は競合とし、別タブで同じ権利を使う開始は1件だけ成功させる。共有経由は権利と進行を変更しないが、認証・同意・オンラインは必須。
- 途中状態は通常・デイリーと別のアカウント別端末キーに保存し、盤面途中状態は端末間同期しない。保存不能なら新規開始を拒否して案内する。開始済み試行は再開で追加消費せず、別アカウントへ流用しない。通信断・ログアウト・失効では保存して一時停止し、本人がオンライン復帰後に再開する。消費後の放棄で権利は返還しない。
- 結果・集計・ランキングは通常8×8・デイリーと分離し、本人の問題IDごとのサーバー登録初回スコアのみ公開する。再挑戦は個人履歴へ残す。共有経由も同じ扱い。正解セルと盤面IDを検証し、同内容の再送は重複として成績を上書きしない。結果送信・公開同意・参考スコア・入力検証・頻度制限は既存方針を維持する。退会・webhook では進行・対象イベント・試行・結果と超級ランキングへの参加を削除する。
- 問題採択は超級だけの公開初回スコアから本人未完了の候補を取り、登録人数最多を優先する。同数時のみ無作為、直近提示・ローカル完了済みも除外。候補ありなら確率で新規生成しない。候補なし・取得や検証失敗の切替でもオンライン条件を再確認し、正解は公開応答へ含めない。共有シードの盤面は候補採択で置き換えない。

### 超級 API と D1（ローカルテスト・ローカル適用済み）

履歴・成績ダイアログはログイン・オンライン時に既存の `GET /api/plays` と `GET /api/super/history` を使い、それぞれ直近500件の完了記録を別モードとして集計する。オフラインでは通常の端末履歴と本人の超級端末記録を使う。超級再送キューの完了レコードには端末表示用の `seedCode` と `capturedAt` を保存し、送信済み記録も保持する。これらはAPIへ送信する `item.body` には含めず、ランキングの正本や再送の内容を変更しない。旧キューはシードがないため、本人の現在の保存盤面と対応する試行だけを補完できる。保存盤面がなくシードを復元できない旧完了キューは最近のプレイへ捏造して表示しない。サーバーの既存履歴はオンラインで引き続き閲覧できる。

- 全ルートで Clerk による本人認証とゲーム名・公開同意を必須とし、許可 Origin・メソッド・JSON形式・4KBの入力上限を検証する。クライアント由来のアカウントIDは使用しない。GET 応答も `no-store` とする。
- `GET /api/super/progress` は本人の `progress` を返す。`POST /api/super/event` は通常シードと `playId`・`cycle` を受け付け、同内容の再送は重複排除、別内容は409とする。1分30件まで新規イベントを受け付け、再送は制限しない。盤面変更の事実自体はクライアント申告であり、競技向けの不正耐性を保証しない。
- `POST /api/super/defer` は `cycle` を受け付け、その世代だけ案内済みにする。古い端末の操作で次の世代の案内状態を変更しない。
- `GET /api/super/candidates` は本人が未完了の超級から問題ID・シード・登録人数だけを最大30件返す。クライアントで直近提示・ローカル完了済みを除外する。
- `POST /api/super/prepare` は超級シードを検証・再生成し、正解を含まない盤面スナップショットを固定して返す。これはまだ挑戦権を消費しない。新規の盤面準備はアカウントごとの暦分で10件まで、固定済みの同じ盤面の再取得は制限しない。
- `POST /api/super/start` は `playId`・`puzzleId`・`entry`（`earned` / `shared`）・`cycle` を受け付ける。登録済みの同内容は成功、別内容は409。権利不足・古い世代は409、未準備の盤面は400。新規開始は1分10件までとし、同内容の再送は制限しない。
- `POST /api/super/complete` は開始済み試行の `playId`・`puzzleId`・正解セル10個・時間・ミス・ヒント数・最大段階を検証する。完了登録と初回スコアの採用を原子的に行い、同内容は重複、別内容の再送は409とする。新規完了は1分10件まで。同じ問題への再挑戦は個人履歴だけに残す。
- `GET /api/super/history` は本人の完了履歴を直近500件まで返す。`GET /api/super/ranking?puzzleId=...` は問題別の初回スコアを既存スコア順で返し、同成績は同順位。上位100人に加えて圏外の本人も返す。本人の真偽値は返すが、アカウントID・試行ID・正解は返さない。
- `0007_super_challenge.sql` は進行・対象イベント・盤面・試行・初回スコア・準備の頻度制限を追加する。イベントの登録と加算、開始登録と消費、完了登録と初回スコア選択は SQL trigger により同一トランザクションで処理する。進行はプロフィールに、イベントと試行は進行に、初回スコアは試行に削除カスケードで紐付け、退会時に本人の関連記録だけを削除する。
- マイグレーションは新Workerより先に適用する。テスト用の非永続D1で検証し、2026-10-09 に通常のローカル開発用D1へ0007を適用した。開発用リモートD1への適用とデプロイは未実施。

## デイリーチャレンジの契約

- 日付キーは日本時間の暦日（`YYYY-MM-DD`）。同じ日付では全アカウントに同じ盤面を返し、作成済み盤面のスナップショットをD1に固定する。公開する盤面データに正解配置は含めない。
- `daily-v1` は通常の `g1`・`g2` シードとは別版とする。8×8上級問題を10×10へ拡張し、追加する2つの1マスRegionにタコを公開する。唯一解と既存Logical Solverによる上級評価を検証する。通常の8×8シード復元・共有には混ぜない。
- `GET /api/daily` は認証済み本人に今日の日付・盤面・挑戦状態を返す。未挑戦では READY を表示し、OK を押した時点で `POST /api/daily/start` により挑戦権を消費する。ゲーム名と公開同意を持つ本人の `playId` を登録し、主キー `(account_id, challenge_date)` により、別端末や再読み込みから新しい試行を作れない。同じ `playId` の再送は重複として扱う。日付の切り替えは日本時間0:00とする。
- 途中状態はアカウント・日付別に端末へ保存し、同じ端末・アカウントで再開できる。盤面途中状態を端末間同期しない。開始済みの別端末に保存がなければ、そこで新たな試行は開始できない。通常問題の保存とは分離する。
- `POST /api/daily/complete` は登録済み `playId`、問題ID、正解セル一式を照合し、未完了の試行だけを原子的に完了する。同じ完了の再送は重複として扱い、成績を上書きしない。接続失敗時はアカウント別の端末キューから再送し、日付が変わっても開始済みの過去日の完了は受け付ける。
- `GET /api/daily/ranking?date=...` は認証済み利用者向け。[`DESIGN.md`](./DESIGN.md) 第19章のスコア降順、同点なら時間・ミス数・ヒント数の昇順で、同成績は同順位。上位100人と、圏外の場合は本人の記録も返す。応答には本人かどうかの真偽値を含めるが、アカウントID・試行ID・正解は含めない。時間・ヒント・ミスはクライアント申告の参考記録とする。
- 退会および `user.deleted` webhook ではデイリーの挑戦記録も削除する。`0006_daily_challenge.sql` は新Workerより先に適用する。開発用 Worker へ反映する場合は、対象を確認したうえで開発用リモート D1 に適用する。
