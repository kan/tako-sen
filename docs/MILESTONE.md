- プレイ中状態の localStorage 保存

## 1. ヒントの学習性

### 目的

ヒントを単なる答え表示ではなく、プレイヤーが定石を理解して次回以降に自力で発見できるものにする。

現状は主に以下のみが存在する。

- Region-Line 消去
- 盤面矛盾の指摘
- 単純な single-candidate

これだけでは、`docs/DESIGN.md` が重視する「段階的に解法を学べるヒント」として不足している。

### 優先して追加するヒント

#### 1.1 あるセルに置くと Region 内の候補がすべて消えるため、そのセルを×にできる

ある候補セルへタコを仮に置いた場合に、別の Region がタコを置ける候補を失うなら、その候補セルにはタコを置けない。

これは brute-force の答えを偽装するのではなく、局所的な制約伝播として説明できる形にする。

必要な表現:

- 仮定するセル
- 影響を受ける Region
- 消えてしまう Region 内候補セル
- 導出される `×`
- 段階的説明文

想定ヒント段階:

1. 注目セルと関連 Region を示す
2. 「ここに置くと、この Region の候補が消える」ことを示す
3. 「各 Region には必ず1つタコが必要」なので仮定セルを除外できると説明する
4. 必要ならそのセルに `×` を適用する

#### 1.2 複数 Region をまたいだ Region-Line

複数の Region の候補が、同じ複数行または複数列に閉じ込められている場合、その行・列にある他 Region のセルを `×` にできる。

例:

- 2つの Region の候補が、同じ2行だけに存在する
- その2行には合計2匹のタコが必要
- したがって、その2行にある他 Region のセルにはタコを置けない

必要な表現:

- 対象 Region 群
- 対象行または対象列の集合
- 対象 Region 群の候補セル
- 除外可能な他 Region セル
- 段階的説明文

### 実装方針

- Technique ごとに独立した関数・テストを持たせる
- Logical Move は UI が再推論しなくてよい構造にする
- Complete Solver の結果だけから「ここが答え」と出すヒントは避ける
- 矛盾検出は通常ヒントより優先する

### 達成条件

- 新規 Technique のユニットテストがある
- ヒントカードが少なくとも注目箇所・パターン・論理的帰結を説明できる
- 既に `×` 済みの内容を同じヒントとして繰り返し出さない
- 同一ヒントの再表示でヒント回数が増えない

## 2. 自動生成の品質

### 目的

プレイヤーが難易度を選び、選んだ難易度に応じて解きやすい問題から遊べるようにする。

現状は、安定性優先で curated puzzle の変形に寄せた実装であり、問題の多様性・難易度制御は不十分。

### 難易度

初期版では以下の3段階を目標にする。

- 初級
- 中級
- 上級

高度な難易度推定を最初から作り込みすぎず、Logical Solver で説明可能な Technique と統計をもとに分類する。

想定する初期基準:

- 初級
  - single-candidate や基本 Region-Line が中心
  - 適用可能なヒントが見つかりやすい
  - 仮定による除外をほぼ要求しない
- 中級
  - 複数 Region をまたいだ Region-Line を含む
  - 次の一手を見つけるために複数制約の組み合わせを見る必要がある
- 上級
  - 「ここに置くと別 Region の候補が消える」型の候補除外を含む
  - 複数の Technique を組み合わせて進める必要がある

### シード表示と復元

各問題にはプレイヤーに見えるシードを持たせる。

必要な機能:

- 現在の問題シードを画面に表示する
- シードをコピーできる
- シードを入力して同じ問題を復元できる
- 難易度とシードの組み合わせで問題が一意に復元される

シードには少なくとも以下を含める方針とする。

- 難易度
- 生成用 seed
- Generator バージョン

Generator の仕様変更で過去 seed の復元性が壊れないよう、Generator バージョンを明示する。

### 実装方針

- 生成結果は必ず Complete Solver で唯一解を検証する
- 難易度分類は Logical Solver の解法ログから行う
- 生成時に以下を収集する
  - 推論ステップ数
  - 使用 Technique
  - Technique ごとの使用回数
  - ヒント候補が途切れるか
  - 確定配置までに必要な消去数
- 初期は生成試行回数に上限を設け、失敗時は明示的に再試行できる UI にする

### 達成条件

- 初級・中級・上級を選んで新規生成できる
- 表示されたシードから同じ問題を復元できる
- 各難易度で生成された問題が唯一解である
- 同一シード・同一難易度から同一問題が生成されるテストがある

## 3. 見やすい Region

### 目的

Region を色だけに依存せず見やすくしつつ、まずは色パレットの改善から着手する。

現状は固定色を Region ID に割り当てているだけで、隣接関係や色覚多様性への配慮が弱い。

### 優先対応

色覚障害があっても比較的区別しやすいとされるカラーパレットを採用する。

候補:

- Okabe-Ito 系のカラーユニバーサルデザイン配色

### 実装方針

- Region ID と表示色は引き続き別概念として扱う
- Region の隣接グラフを作り、隣接 Region が近い色になりにくいように割り当てる
- 完全ランダムな色割り当てはしない
- 境界線は色とは別に明確化する

### 達成条件

- Region 表示色がカラーユニバーサルデザインを意識したパレットになっている
- 隣接 Region に同色または近すぎる色が割り当たらない
- Region ID を色として扱う実装になっていない
- スマートフォンサイズで Region 境界が見分けやすい

## 4. 快適さ

### 目的

`×` やタコの設置が軽快で気持ちよく、タコ確定だけは意図的に少し重い操作として感じられるようにする。

### 優先対応

#### 4.1 マーク設置時のアニメーション

対象:

- `×` の追加
- `×` の削除
- タコの正解配置
- 誤配置による固定赤 `×`
- ショートカットによる複数 `×` の一括配置

方向性:

- 通常 `×` は軽く素早いフィードバック
- タコ確定は少し重みのあるフィードバック
- 誤配置は明確に分かるが、過度に攻撃的にしない
- ショートカットの一括配置は、まとめて整理された感覚が出るようにする

#### 4.2 バイブレーション

対応端末では Vibration API を利用して触覚フィードバックを出す。

想定:

- 通常 `×`: 短い振動
- 正しいタコ確定: 少し長め
- 誤配置: 異なるパターン
- CLEAR: 達成感のある短いパターン

注意:

- Vibration API が使えない環境では何もしない
- 設定で無効化できるようにする
- アクセシビリティ上、振動に依存した情報伝達にしない

### 実装方針

- Core にはアニメーションやバイブレーションを持ち込まない
- UI 操作結果をもとに Vue 側で演出する
- ゲーム進行に必要な情報を演出だけに依存させない
- 過度なアニメーションで盤面が騒がしくならないようにする

### 達成条件

- `×` とタコ設置時に視覚フィードバックがある
- 対応端末では触覚フィードバックがある
- 振動を無効化できる
- 演出なしでもゲーム状態が理解できる

## 推奨実装順

1. ヒントの学習性を改善する
2. シード表示・復元を追加する
3. 難易度別 Generator の評価基盤を作る
4. Region 色パレットと隣接色割り当てを改善する
5. アニメーションとバイブレーションを追加する
6. 難易度別 Generator の品質を上げる

理由:

- ヒントと Logical Solver は Generator の難易度評価にも使うため、先に強化する
- シード復元は Generator 改善中の不具合再現に必要
- 視認性と快適さはプレイ感に直結するが、Core の難易度評価基盤とは独立して進められる
