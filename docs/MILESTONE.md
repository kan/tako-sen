## 1. ヒントの学習性

ステータス: **完了**

現在のプロトタイプで優先していたヒント改善は実装済みです。

実装済み:

- 矛盾検出を通常ヒントより優先
- single-candidate
- 基本 Region-Line
- 複数 Region をまたいだ Region-Line
- 「あるセルへ置くと別 Region の候補がすべて消える」型の候補除外
- 確定済みタコから分かる `×` の置き忘れ
- Logical Move に、UI が再推論しなくても説明・ハイライトできる情報を追加
- 同一ヒントの再表示ではヒント回数を増やさない
- クリア後はヒントを出さず、ヒントボタンも非表示
- 各 Technique とヒント UI 判定の回帰テスト

### 目的

ヒントを単なる答え表示ではなく、プレイヤーが定石を理解して次回以降に自力で発見できるものにする。

以前は主に以下のみが存在していた。

- Region-Line 消去
- 盤面矛盾の指摘
- 単純な single-candidate

この不足は、上記の追加 Technique と UI 側のヒント制御で改善済み。

### 優先して追加するヒント

#### 1.1 あるセルに置くと Region 内の候補がすべて消えるため、そのセルを×にできる

ある候補セルへタコを仮に置いた場合に、別の Region がタコを置ける候補を失うなら、その候補セルにはタコを置けない。

これは brute-force の答えを偽装するのではなく、局所的な制約伝播として説明できる形にする。

必要な表現:

- 仮定するセル
- 影響を受ける Region
- 消えてしまう Region 内候補セル
- 導出される `×`
- 段階的説明文

想定ヒント段階:

1. 注目セルと関連 Region を示す
2. 「ここに置くと、この Region の候補が消える」ことを示す
3. 「各 Region には必ず1つタコが必要」なので仮定セルを除外できると説明する
4. 必要ならそのセルに `×` を適用する

#### 1.2 複数 Region をまたいだ Region-Line

複数の Region の候補が、同じ複数行または複数列に閉じ込められている場合、その行・列にある他 Region のセルを `×` にできる。

例:

- 2つの Region の候補が、同じ2行だけに存在する
- その2行には合計2匹のタコが必要
- したがって、その2行にある他 Region のセルにはタコを置けない

必要な表現:

- 対象 Region 群
- 対象行または対象列の集合
- 対象 Region 群の候補セル
- 除外可能な他 Region セル
- 段階的説明文

### 実装方針

- Technique ごとに独立した関数・テストを持たせる
- Logical Move は UI が再推論しなくてよい構造にする
- Complete Solver の結果だけから「ここが答え」と出すヒントは避ける
- 矛盾検出は通常ヒントより優先する

### 達成条件

- [x] 新規 Technique のユニットテストがある
- [x] ヒントカードが少なくとも注目箇所・パターン・論理的帰結を説明できる
- [x] 既に `×` 済みの内容を同じヒントとして繰り返し出さない
- [x] 同一ヒントの再表示でヒント回数が増えない

## 1.5 操作性とプロトタイプ UI の改善

ヒント改善と並行して、実プレイ中に不便だった操作を改善しました。

実装済み:

- `×` の連続入力
  - 盤面上で押したままスライドすると、通過したセルへ `×` を追加する
  - 一定距離以上動いた時点で長押し判定をキャンセルし、タコ誤配置を避ける
- タコ確定操作の調整
  - 長押し時間に到達してから枠を表示する
  - 枠が出た状態で指やマウスを離すとタコを確定する
  - 枠が出た後にマス外へ移動した場合はキャンセルする
  - 長押し成立直後の release / click 競合で `×` が出ないよう、pointer release 判定をテスト可能な関数へ分離
- ダブルクリック補完の整理
  - タコ未設置セルでは補完を実行しない
  - 確定済みタコからの補完対象に、同じ Region のセルを追加
- 盤面リセット
  - 現在の問題はそのまま、`×`、タコ、固定エラー、ミス数、ヒント使用数をクリアする
- クリア後 UI
  - クリア済みではヒントを出さず、ヒントボタンとヒントカードを非表示にする
- ヘッダー表示
  - 説明文を減らし、`TAKO-SEN` タイトルと `PROTOTYPE` バッヂを中心にした表示へ変更

補足:

- 操作判定やショートカット判定は、可能な範囲で pure function 化し、回帰テストを追加済み。

## 2. 自動生成の品質

ステータス: **評価基盤と UI は実装済み・品質改善を継続**

### 目的

プレイヤーが難易度を選び、選んだ難易度に応じて解きやすい問題から遊べるようにする。

seed から作る候補を優先し、条件に合う候補がなければ curated puzzle にフォールバックする。Logical Solver による初期の難易度分類は実装済みだが、多様性と分類精度には改善余地がある。

### 難易度

初期版では以下の3段階を目標にする。

- 初級
- 中級
- 上級

高度な難易度推定を最初から作り込みすぎず、Logical Solver で説明可能な Technique と統計をもとに分類する。

想定する初期基準:

- 初級
  - 最初から1マス、または1ラインに限定された Region が存在する
  - 必要に応じて、1つの Region のタコを公開済み初期配置として置く
  - single-candidate や基本 Region-Line / Line-Region が中心
  - 複数 Region-Line や仮定による除外を要求しない
- 中級
  - 複数 Region をまたいだ Region-Line までを使えば解ける
  - 仮定による候補除外は要求しない
  - 次の一手を見つけるために複数制約の組み合わせを見る必要がある
- 上級
  - 「ここに置くと別 Region の候補が消える」型の候補除外を含む
  - 複数の Technique を組み合わせて進める必要がある

### シード表示と復元

各問題にはプレイヤーに見えるシードを持たせる。

実装済み:

- 現在の問題シードを画面に表示
- シードをクリップボードへコピー
- 表示されたシードを入力して同じ問題を復元
- 「ローカル成績」の最近のシードから同じ問題を復元
- 難易度と Generator バージョンをシード文字列に含める
- 同一シード・同一難易度から同一問題を復元する回帰テスト

必要な機能:

- [x] 現在の問題シードを画面に表示する
- [x] シードをコピーできる
- [x] シードを入力して同じ問題を復元できる
- [x] 難易度とシードの組み合わせで問題が一意に復元される

シードには少なくとも以下を含める方針とする。

- [x] 難易度
- [x] 生成用 seed
- [x] Generator バージョン

Generator バージョンを明示して、異なる版の問題を同じシードとして扱わない。現状の復元 UI は現行バージョンのみを受け付けるため、将来の Generator 更新時に旧版コードの復元を維持するには別途対応が必要。

補足:

- 「初級・中級・上級」は復元キーであると同時に、生成候補の評価目標として使用している。画面の「評価」は実際に採用された問題の分析結果であり、選択した難易度と異なる場合がある。

### 実装方針

- 生成結果は必ず Complete Solver で唯一解を検証する
- [x] 難易度分類は Logical Solver の解法ログから行う
- [x] 生成時に以下を収集する
  - [x] 推論ステップ数
  - [x] 使用 Technique
  - [x] Technique ごとの使用回数
  - [x] ヒント候補が途切れるか
  - [x] 確定配置までに必要な消去数
- [x] 指定難易度に合う評価結果の候補を優先して採用する
- [x] 生成試行回数に上限を設け、条件に合う候補が見つからなければ近い候補を採用する

補足:

- `analyzePuzzleDifficulty` と `generatePuzzleWithAnalysis` で評価基盤を追加済み。
- `generatePuzzleWithAnalysis` は試行上限内で指定難易度に合う候補を探し、見つからない場合は近い候補へフォールバックする。
- 初級はランダム探索だけでは上級寄りになりやすいため、1〜2個の1マスRegionを導入用に固定した候補を seed から構築する。
- 公開済みタコは難易度調整の補助手段として扱い、原則0匹、必要な場合でも1匹までに留める。
- 現時点の分類は、対応済み Logical Solver で解ける範囲における初期の相対分類。問題の多様性や分類精度の改善は後続で行う。

### 達成条件

- 初級・中級・上級を選んで新規生成できる
- 表示されたシードから同じ問題を復元できる
- 各難易度で生成された問題が唯一解である
- 同一シード・同一難易度から同一問題が生成されるテストがある

## 3. 見やすい Region

ステータス: **初期対応は完了**

### 目的

Region を色だけに依存せず見やすくしつつ、まずは色パレットの改善から着手する。

当初は固定色を Region ID に割り当てていたが、現在は Region の隣接関係を使った表示色割り当てと境界線表示に変更済み。

### 優先対応

色覚障害があっても比較的区別しやすいとされるカラーパレットを採用する。

候補:

- Okabe-Ito 系のカラーユニバーサルデザイン配色

実装済み:

- Okabe-Ito 系を意識した Region 表示パレットへ変更
- Region の隣接グラフから表示色を割り当て
- 8つの Region すべてに異なる表示色を割り当て
- 隣接 Region が同じ表示色にならないことをテストで確認
- セルごとの Region 境界を Region 差分から太線表示
- 固定 CSS の `data-region` 色指定を廃止し、Region ID と表示色を分離

補足:

- 簡易的な色覚シミュレーションでは、一部の色ペアは近く見える可能性がある。
- ただし現状は Region 境界を太線で示しており、色だけを唯一の識別手段にはしていない。
- 盤面が騒がしくなるリスクを避けるため、パターン表示は現時点では導入しない。
- 公開品質でさらに詰める場合は、色パレットの再調整または控えめなパターン表示を検討する。

### 実装方針

- [x] Region ID と表示色は引き続き別概念として扱う
- [x] Region の隣接グラフを作り、隣接 Region が近い色になりにくいように割り当てる
- [x] 盤面上の全 Region に異なる表示色を割り当てる
- [x] 完全ランダムな色割り当てはしない
- [x] 境界線は色とは別に明確化する

### 達成条件

- [x] Region 表示色がカラーユニバーサルデザインを意識したパレットになっている
- [x] 隣接 Region に同色または近すぎる色が割り当たらない
- [x] 非隣接でも同じ表示色を使わない
- [x] Region ID を色として扱う実装になっていない
- [x] スマートフォンサイズで Region 境界が見分けやすい

## 5. クリア時のゲーム的処理の整備

ステータス: **ローカル版を実装済み**

実装済み:

- 匿名ユーザー ID とプレイ履歴を localStorage に保存
- ×またはタコで盤面が変化した時点で試行を記録（何も置かずに次の問題へ進んだ場合はカウントしない）

- 最近のシードはリンクから盤面を復元できる
- READY 画面の OK から計時し、一時停止中・再読み込み後の待機中はクリア時間に含めない
- 現在の盤面保存と履歴保存を別のキーに分離

### 目的

単に盤面を解いて終わりではなく、プレイ結果を記録し、同じシードや難易度での成績を比較できるようにする。

初期段階ではローカル保存のみを前提に設計・実装し、仕様が固まってから Cloudflare Workers API としてオンラインサービス化する。

この段階では、オンラインアカウント、クラウド同期、全ユーザー共有ランキングはスコープ外とする。

### 記録するプレイ結果

シードごとに、盤面が初めて変わった時点で進行中の試行を記録し、クリア時に以下を確定する。

- シード
- Generator バージョン
- 難易度
- クリア日時
- クリア時間
- ミス数
- ヒント使用数
- 完了状態（進行中・クリア済み）
- 必要に応じて、盤面の構造署名または問題署名

### シード別ランキング

同一シード・同一難易度・同一 Generator バージョンの結果を比較できるようにする。

初期のローカルランキング基準:

- クリア時間が短いほど上位
- 同時間に近い場合は、ヒント使用数が少ないほど上位
- さらに同等なら、ミス数が少ないほど上位

補足:

- ローカル保存では、同一端末内の自分の記録ランキングとして扱う
- オンライン化時には、同じ集計軸を Cloudflare Workers API 側へ移行できるようにする

### ユーザー別集計

ローカルユーザー単位で、プレイ傾向を確認できるようにする。

実装済みの集計:

- 総プレイ数
- クリア数
- 難易度別クリア数
- 難易度別平均クリア時間
- 難易度別平均ミス数
- 難易度別平均ヒント使用数
- 自己ベスト更新数
- 最近プレイしたシード

補足: 「総プレイ数」は `×` またはタコの操作で盤面が実際に変わった試行だけを数える。ヒントだけを見て次の問題へ進んだ場合も、盤面を変更していなければ数えない。

### ユーザーセッション

初期版では、ローカル保存のみで匿名ユーザーセッションを確立する。

方針:

- 初回起動時にローカルの `userId` を生成して保存する
- `userId` は個人情報を含まないランダム ID とする
- プレイ結果はこの `userId` に紐付ける
- localStorage または小さな永続化インターフェースの背後に隠す
- 将来 Cloudflare Workers API 化する際は、このローカルセッションを移行・同期できる設計にする

### 実装方針

- まずはローカル保存で結果記録・ランキング・集計を実装する
- 永続化処理は Core から分離し、小さなインターフェースの背後に置く
- ゲーム中状態の保存と、完了済み結果の保存を分ける
- クリア判定時に一度だけ結果を確定し、同じクリアを重複記録しない
- シード復元で同じ問題を遊んだ場合も、同じランキング軸に入るようにする
- Cloudflare Workers API 化を前提に、保存データの型を明示しておく

### 達成条件

- クリア時に結果がローカルへ記録される
- 同一シードのローカルランキングを表示できる
- 難易度別のローカル集計を表示できる
- ローカル匿名ユーザーセッションが作成・保持される
- 将来 API 化しやすい保存データ構造になっている

## 6. 快適さ

ステータス: **未着手**

### 目的

`×` やタコの設置が軽快で気持ちよく、タコ確定だけは意図的に少し重い操作として感じられるようにする。

### 優先対応

#### 6.1 マーク設置時のアニメーション

対象:

- `×` の追加
- `×` の削除
- タコの正解配置
- 誤配置による固定赤 `×`
- ショートカットによる複数 `×` の一括配置

方向性:

- 通常 `×` は軽く素早いフィードバック
- タコ確定は少し重みのあるフィードバック
- 誤配置は明確に分かるが、過度に攻撃的にしない
- ショートカットの一括配置は、まとめて整理された感覚が出るようにする

#### 6.2 バイブレーション

対応端末では Vibration API を利用して触覚フィードバックを出す。

想定:

- 通常 `×`: 短い振動
- 正しいタコ確定: 少し長め
- 誤配置: 異なるパターン
- CLEAR: 達成感のある短いパターン

注意:

- Vibration API が使えない環境では何もしない
- 設定で無効化できるようにする
- アクセシビリティ上、振動に依存した情報伝達にしない

### 実装方針

- Core にはアニメーションやバイブレーションを持ち込まない
- UI 操作結果をもとに Vue 側で演出する
- ゲーム進行に必要な情報を演出だけに依存させない
- 過度なアニメーションで盤面が騒がしくならないようにする

### 達成条件

- `×` とタコ設置時に視覚フィードバックがある
- 対応端末では触覚フィードバックがある
- 振動を無効化できる
- 演出なしでもゲーム状態が理解できる
