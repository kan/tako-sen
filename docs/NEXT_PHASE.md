## 基本方針

- 未ログインでも従来どおり問題生成・プレイ・ローカル保存を使える。通信失敗はゲーム進行を止めない。
- 「オンラインプレイ」の第一段階は、同じ問題をリンクで共有し、各自が非同期に解いて結果を比較する機能とする。同時対戦・協力プレイは対象外とする。
- アカウントはオンライン履歴の所有権と端末間同期のために導入する。ローカル匿名IDを認証済みアカウントの証明として扱わない。
- 公開ランキングはローカル順位と別概念とする。ヒントを使うことを失敗として扱わない。
- Coreのパズルロジックは引き続きブラウザ・テストから独立して利用できるようにする。

#### 基本仕様

- デイリーと同じ10×10・10 Region・10匹の高難易度盤面を「超級」として提供する。ルール・対応定石・盤面の品質基準はデイリーに準じ、日付固定や1日1回というデイリー固有の制限は引き継がない。同じ日のデイリー盤面そのものを提供するという意味ではない。
- 超級はデイリーと同様にオンライン・ログイン専用機能とする。未ログイン時はログインへ誘導し、オフラインでは新たな挑戦を開始しない。通常8×8の未ログイン・オフラインプレイは引き続き維持する。
- 超級の問題選択も通常問題と同じ方針とし、超級の公開ランキングに記録があり、本人の完了履歴がない未プレイ盤面のうち、登録人数が最多の盤面を優先する。同数なら無作為に選び、端末内で直近に提示した盤面とローカル完了済みの同一シードも避ける。候補がある場合は確率による新規生成を行わず、候補がなければ新規生成する。取得・検証失敗時の再試行・生成への切替はオンライン・ログイン条件を満たす範囲だけで行い、オフライン開始への抜け道にはしない。
- 初級・中級・上級の通常問題を10回クリアすると、超級へ1回挑戦できる。難易度を切り替えても共通のカウントとする。
- 10回に到達したら「超級に挑戦しますか？」のダイアログを表示する。
- スキップしても挑戦権を失わず、任意のタイミングで1回挑戦できる。保留できる挑戦権は1回分だけとし、保留中の通常クリアは次の10回へ加算しない。超過分の繰り越しや挑戦権の積み増しはしない。
- 画面に王冠アイコンと「あとX」を表示する。挑戦権の保留中は残り回数を省き、王冠の開始導線だけ表示する。「超級に挑戦できます」や同期完了のメッセージは表示しない。
- 超級の共有シードからの挑戦は、この回数制限の対象外とする。オンライン・ログイン条件は共有経由でも必須だが、挑戦権がなくても遊べ、保留中の挑戦権も消費しない。共有では指定された盤面を開き、登録人数による問題選択で置き換えない。共有による超級プレイ自体は通常問題10回のカウントに含めない。
- ヒント・ショートカットは既存方針を維持し、挑戦権をヒント用の消費アイテムとして扱わない。通常の8×8プレイを強制的に超級へ切り替えない。

#### カウントと挑戦権の状態遷移（承認済み）

解放条件は通常問題のクリア数とする。最初の盤面変更では対象アカウントとサイクルの試行情報だけを保持し、サーバー検証済みの完了記録との照合に成功した時点で1回と数える。同一シードへの再挑戦も別試行のクリアなら数える。試行数からの移行時は、途中の進捗を現在サイクルの対象試行のうちクリア済みの数へ数え直し、獲得済みの挑戦権は保持する。

| 状態                                   | 通常問題の対象試行がクリア済みと確認される | 超級への操作                                          |
| -------------------------------------- | ------------------------------------------ | ----------------------------------------------------- |
| カウント中（0〜8回）                   | 1回加算する                                | 通常の超級開始導線は利用不可。共有シードは利用可      |
| カウント中（9回）                      | 1回分の挑戦権を獲得し、案内待ちへ移る      | 安全な画面遷移時に挑戦確認を表示する                  |
| 挑戦権あり（案内待ち・保留・開始準備） | 加算しない                                 | 「挑戦する」で準備へ進む。「あとで」で1回分を保留する |
| 挑戦開始が確定                         | 次のカウントを0回から再開する              | 挑戦権を消費し、その試行を開始する                    |

- 同一 `playId` の連続操作・クリア・一時停止・復元・再読み込みで重複加算しない。READYのOK、未操作で次の問題へ進む操作、ヒント閲覧だけでは数えない。
- デイリー・超級・チュートリアルの試行は加算対象外。通常8×8の共有・シード復元・再挑戦は、上記の通常試行の定義に従って扱う。
- 保留中に遊んだ通常試行を、挑戦権消費後に遡って加算しない。消費後に始まる対象試行から新しく数える。
- 挑戦権を消費するタイミングは、盤面生成・検証・保存に成功し、超級READYのOKでサーバーへの開始登録が成功した時点とする。ダイアログへの同意、生成失敗、READYでの取り消しだけでは消費しない。
- 開始済みの超級を再読み込みして続ける場合は同じ試行の再開であり、追加の挑戦権を要求しない。開始後に諦めても消費済みの権利は戻さない。

#### 画面導線とタイマー（承認済み）

- 通常プレイ画面の難易度・問題操作に近い位置へ、控えめな残り回数表示と超級への導線を置く。保留してもメニューを探さず挑戦できるようにする。
- 10回目のクリアをサーバーが確認した時に権利を獲得するが、入力ジェスチャーやプレイ中の推論を遮らない。現在の問題のクリア後、または次の問題へ進む時などの区切りで確認ダイアログを表示する。既存のクリア・ヒント等のダイアログには重ねない。未ログイン・名前や公開同意の未設定・挑戦権なしでも超級ボタンから説明ダイアログを開き、必要な設定やログインへ進める。
- ダイアログは「挑戦する」「あとで」を用意し、閉じる・Escape・背景タップも「あとで」と同じ扱いにする。保留後は通常問題を遊ぶたびに自動表示せず、利用者が超級の導線から開始する。
- 案内待ちと案内済みの保留を区別して保存し、再読み込みで同じ案内を繰り返さない。案内前に閉じた場合は、次の安全な区切りで案内する。
- 超級への移動前に、未クリアの通常盤面を置き換えることを明示する。ダイアログを開くだけで現在の盤面を破棄しない。確認中は計時を停止し、キャンセル後の復帰は既存のモーダル・READYの仕様に合わせる。

### 生成の方法

現在の方法（初級の盤面から出発して境界を動かす）をやめ、次の 3 段で作る。8×8 と 10×10 で同じ方法を使う。

1. 正解を決め、正解のマスを種に Region を成長させる。いちばん小さい Region を優先して育て、極端に小さい Region ができるのを防ぐ。初級だけ、Region を 1 個選んで 1 マスのままにする。
2. 境界のマスを隣の Region へ 1 マスずつ移し、解の個数が 1 になるまで減らす。解の個数を増やす移動は採らない。
3. 唯一解と、定石だけで解けることを保ったまま、指定の難易度と形の制約を満たすまで境界を動かす。難易度から遠ざかる移動は採らない。

- 時間では打ち切らず、手数と試行回数で打ち切る。同じ seed からは、ブラウザとサーバーのどちらでも同じ盤面ができる。
- 16 回の試行で条件を満たせなければ、定石で解ける唯一解の盤面のうち条件に最も近いものを返す。どの試行もそこに届かなければ例外にする。試作の 700 件では、どちらも 0 件だった。
- 新規生成では、例外になった時と、評価が指定難易度と違った時に、別の seed を 3 回まで引き直す。シードコードの復元では引き直さず、作れない旨を表示する。
- 難易度の判定そのもの（どの定石を使えば上級か）は変えない。上級の下限は、生成側が盤面を採用する条件として課す。

試作の計測（開発機）は次のとおり。全件が唯一解で、定石だけで解ける。

| 対象  | 件数 | 指定難易度に一致 | 1 マス Region     | 開始直後に置けるタコ | 生成時間（中央値 / p95 / 最大） |
| ----- | ---: | ---------------- | ----------------- | -------------------- | ------------------------------- |
| 初級  |  200 | 200              | 全件ちょうど 1 個 | 全件ちょうど 1 匹    | 113 / 530 / 1,063 ms            |
| 中級  |  200 | 200              | 全件 0 個         | 全件 0 匹            | 73 / 252 / 470 ms               |
| 上級  |  200 | 200              | 全件 0 個         | 全件 0 匹            | 96 / 293 / 582 ms               |
| 10×10 |  100 | 100              | 全件 0 個         | 全件 0 匹            | 246 / 1,243 / 1,601 ms          |

10×10 は、最初の試作では中央値 1.2 秒、最大 14.8 秒かかった。次の 2 つで上の時間まで短くなった。

- 解の個数を、境界を動かした時に変わる分だけ数え直す。数え上げは正確なままなので、探索の精度は落ちない。
- 難易度の判定を配列とビット演算で書き直す。既存の実装と 475 盤面で結果が一致した。旧版の盤面は変わらず、旧版の生成も速くなる。

### 10×10 の方式の比較

速度の問題への対処として、次の 3 つを比べた。

| 観点                   | 事前に生成して D1 に置く                       | その場で生成する                 | 採用: 超級はその場、デイリーは前日 |
| ---------------------- | ---------------------------------------------- | -------------------------------- | ---------------------------------- |
| 超級を始める時の待ち   | 数十 ms                                        | 開発機で p95 1.2 秒、最大 1.6 秒 | その場で生成と同じ                 |
| デイリーを開く時の待ち | なし                                           | その日の最初の人だけ 1〜2 秒     | なし                               |
| 追加で必要なもの       | 在庫の表、払い出しの API、補充、在庫切れの処理 | 生成器の高速化だけ               | デイリー用の定期実行だけ           |
| seed からの再現        | できる                                         | できる                           | できる                             |

超級は通常問題を 10 回クリアして 1 回の頻度なので、1 秒前後の待ちを受け入れる。在庫の仕組みを持たずに済み、seed だけで再現できる。デイリーは日付が決まっていて 1 日 1 盤面なので、前日に作る負担が小さい。

スマートフォンで超級の生成が p95 で 3 秒を超える場合は、超級にも在庫方式を足す。その場合の設計（`super_puzzles` を在庫として使い、払い出しの API を足す）は試作の報告にあり、後から追加できる。

試作のコードと計測の出力は作業用の一時ディレクトリにあり、リポジトリには入っていない。実装では試作を移植し、計測は G2 から G4 の監査テストで再現する。

### G1 と G2 の実装結果（2026-10-11）

計画から変えた点と、実装中に分かったことを記す。

- 解の個数の差分での数え直しは、10×10 だけに使う想定だった。8×8 に使っても同じ盤面ができ、時間も短くなったので、8×8 と 10×10 で同じ経路を使う。
- 品質チェックの中で、盤面を変えずに生成を速くする方法が 3 つ見つかった。固定したタコの列と Region を探索の最初に使う、保存された正解と印が食い違わない間は矛盾の探索を省く、境界を動かした後の唯一解の判定を動かしたマスだけで行う、の 3 つ。試作と同じ盤面のまま、10×10 は中央値 235 ms から 85 ms、最大 1,967 ms から 399 ms になった（開発機、30 件）。8×8 は中央値 15 ms 前後、最大 130 ms 前後（各 60 件）。
- `g3` は試行回数の指定（`maxAttempts`）を読まない。読むと、同じシードコードから別の盤面を作れてしまう。
- 保存された正解が盤面に合わない場合の矛盾判定を、同値性テストが通っていなかった。その場合を含む盤面を足した。
- `g2` の盤面はこれまで固定ハッシュで守られていなかった（`g1` だけ）。解析の置き換えの前後で `g2` の 129 件が一致することを確認し、`g2` と `g3` の固定ハッシュを足した。
- 起動時に生成する固定 seed の盤面は、保存された盤面がない初回の利用者の最初の問題になる。`g3` で生成する。

10×10 の生成が最大 0.4 秒まで短くなったので、超級をその場で生成する方式は、スマートフォンでも成立する見込みが高くなった。実機での計測は G5 で行う。

### G3 の実装結果（2026-10-11）

- 新しい超級は `super-v2` で作る。10×10 を直接生成し、事前設置はない。`super-v1` のシードコード、端末に保存した途中の盤面、履歴、ランキングは引き続き使える。
- 超級のシードコードは版と seed の組として読む。盤面の版がコードの版と一致することを、端末の保存、サーバーの準備応答、途中保存の 3 か所で確認する。
- 準備 API は、前後に空白の付いたシードコードを拒否する。コードは書かれたまま保存し、候補を接頭辞で選ぶため。画面は空白を除いてから送るので、利用者の操作は変わらない。
- 「他のプレイヤーの記録がある盤面」の候補は `super-v2` だけにした。`super-v1` の盤面は、共有されたコードと履歴からだけ開ける。
- `super-v2` は、難易度と形の条件をすべて満たした盤面だけを返す。`g3` のように「条件に最も近い盤面」で代用しない。条件に届かない seed では盤面を返さず例外にする。画面は別の seed を 3 回まで引き直し、サーバーはその seed を `400` で拒否する。固定コーパスの 300 seed では 1 件も起きなかった。
- 300 seed の全盤面が条件を満たした。唯一解、定石で解ける上級、事前設置なし、Region は 3〜18 マス、開始直後に置けるタコなし、Region 枯渇を 2 回以上。生成時間は中央値 102 ms、p95 396 ms、最大 806 ms（開発機）。
- 超級の盤面には固定ハッシュがなかった。`super-v1` と `super-v2` の各 3 件を足した。`super-v1` の 3 件は変更前のコードが作る盤面と一致する。

### G4 の実装結果（2026-10-13）

- 切り替え日（`DAILY_V2_START_DATE`）以降の日付は `daily-v2` で作る。`super-v2` と同じ設定で 10×10 を直接生成し、事前設置はない。乱数の入力と問題 ID に版が入るので、同じ文字列を seed にした超級とは別の盤面になる。
- `daily_puzzles` に `generator_version` 列を足した（`0012_daily_version.sql`）。既存の行は `daily-v1` になる。計画では日付から版を決める関数を読み戻しにも使うとしていたが、読み戻しでは保存された版を使う。切り替え日を動かしても、作成済みの盤面の版は変わらない。日付から版を決めるのは、盤面を新しく作る時だけ。
- 1 つの日付につき seed を 8 個まで試す。最初の seed が条件を満たさない日のための予備。2026-10-16 から 400 日分では、全日が最初の seed で条件を満たした。8 個とも届かない日は盤面を作れず、その日のデイリーは開けない。
- 定期実行は毎日 14:00 UTC（日本時間 23:00）に動き、翌日の盤面を保存する。保存済みなら何もしない。対象の日付は、実行の予定時刻から決める。作れていない日は、その日の最初のリクエストで作る。
- 400 日分の全盤面が条件を満たした。唯一解、定石で解ける上級、事前設置なし、Region は 3〜18 マス、形の制約の違反なし、開始直後に置けるタコなし、Region 枯渇を 2 回以上。生成時間は中央値 139 ms、p95 589 ms、最大 1,577 ms（開発機）。
- `daily-v2` の固定ハッシュを 3 件足した。`daily-v1` の固定ハッシュは変更なしで通る。

デプロイの時の注意は次のとおり。

- `0012` を新しい Worker より先に適用する。先に Worker を出すと、列がないためデイリーの API がすべて失敗する。
- デプロイ前から開いたままの画面は `daily-v1` しか復元できない。切り替え日にその画面でデイリーを開くと復元に失敗し、再読み込みするまで始められない。切り替え日をデプロイの翌々日以降にすると、該当する画面は減る。

### g4: 初級と中級の難易度の調整（2026-10-13）

ステータス: **実装済み、開発環境へは未反映**。作業段階の G4（`daily-v2`）とは別で、8×8 の生成器の版 `g4` を指す。

`g3` を開発環境で遊んだ人から、旧版より難しくなった、特に初級が難しいとの意見があった。利用者も、中級、上級、超級を含めて同じ体感だった。`g2` と `g3` を各 150 盤面で比べた結果は次のとおり（平均）。

| 指標                                  | 初級 `g2` | 初級 `g3` | 中級 `g2` | 中級 `g3` | 上級 `g2` | 上級 `g3` |
| ------------------------------------- | --------: | --------: | --------: | --------: | --------: | --------: |
| 定石なしで全部置ける盤面              |       40% |        0% |        3% |        0% |        0% |        0% |
| 開始直後に置けるタコ                  |    4.8 匹 |    1.0 匹 |    1.5 匹 |      0 匹 |    2.0 匹 |      0 匹 |
| 消去の定石の回数                      |       1.2 |       3.0 |       3.8 |       3.4 |       5.6 |       8.6 |
| 最初の 1 匹までに難しい定石が要る盤面 |         — |         — |       14% |       89% |        7% |       85% |

「消去の定石」は、タコを置く前に × で候補を減らす 4 つの定石。「難しい定石」は、そのうち複数 Region の定石と Region 枯渇を指す。

- 初級の `g3` は、開始直後に置けるタコを 1 匹に固定していた。1 匹目の後は必ず消去の定石が要り、消去の回数は `g2` の中級に近かった。
- 中級と上級の `g3` は、1 匹も置けていない盤面で難しい定石を見つける必要があった。旧版では、何匹か置いて盤面が整理されてから難しい定石が出てきた。

利用者の提案で、「最初の 1 匹と × を置くだけで次のタコが決まるか」を採用条件にした。試作版をローカルで遊び比べて決めた条件は次のとおり。

| 難易度         | `g4` の条件                                                                               | 決めた経緯                                                         |
| -------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 初級           | 消去の定石なしで置けるタコが 2〜3 匹（1 マス Region の 1 匹を含む）。消去の定石は 1〜2 回 | 3〜4 匹の案とも遊び比べ、体感の差が小さかったので 2〜3 匹にした    |
| 中級           | 最初の 1 匹まで、基本の消去の定石 2 回以内で届く。複数 Region の定石は 1 匹目より後       | 利用者が試作を遊び、ちょうど良いと判断した                         |
| 上級           | `g3` と同じ                                                                               | 中級と同じ条件の試作も遊んだ上で、利用者が今のままにすると判断した |
| 超級とデイリー | 変えない（`super-v2`、`daily-v2` のまま）                                                 | 利用者の判断                                                       |

- 形の制約と事前設置なしは `g3` と同じ。1 マス Region は初級の 1 個だけで、最初から見えている確定マスは増えない。
- 難易度の分類（どの定石を使えば初級、中級、上級か）は変えていない。生成器が盤面を採用する条件を足した。
- 中級の条件は、`g3` の予算（試行 16 回、調整 400 手）では 200 件中 26 件が届かなかった。試行 48 回、調整 800 手で 0 件になった。`g4` は全難易度でこの予算を使う。
- 各難易度 300 seed の全盤面が条件を満たした。生成時間（開発機、中央値 / p95 / 最大）は、初級 21 / 101 / 389 ms、中級 87 / 279 / 642 ms、上級 16 / 56 / 95 ms。中級は `g3`（13 / 55 / 159 ms）より遅い。
- 新規生成の既定、「次の問題」の候補、シードコードの入力例は `g4` になる。`g3` の盤面は、共有、復元、履歴、ランキングで引き続き使える。切り替えの直後は、記録のある `g4` の盤面がないので、候補は出ず、端末で生成する。
- 条件に届かない seed では、評価が同じでも、最初の 1 匹までに要る消去が多い盤面を返すことがある。新規生成の引き直しは評価だけを見るので、その盤面はそのまま出る。確認した seed では起きていない。

監査の結果は `GENERATOR_AUDIT.md`「g4 の監査」に記す。

### ID 基盤の仕様

vegtab の匿名認証（`backend/src/routes/auth.ts`、`backend/src/lib/refresh-tokens.ts`、マイグレーション `0004` `0008` `0009`）を出発点にする。ただし資格情報の持ち方は、端末のストレージに置く `deviceId` と Bearer トークンではなく、`kan-game.app` 全体へ届く Cookie に変える。ストレージはオリジンごとに分かれ、サブドメイン間で ID を共有できないため。

- 発行: ID 基盤の API に Cookie なしで初めて届いたリクエストで、新しい ID と署名付きのセッション Cookie を発行する。Cookie は `Domain=kan-game.app; Secure; HttpOnly; SameSite=Lax` とし、サーバーの応答ヘッダーで設定する。有効期限はブラウザの上限（約 400 日）に合わせ、アクセスのたびに延長する。
- 発行元の経路: 各ゲームの Worker が `/api/id/*` を Service Binding で ID 基盤の Worker へ中継する。画面から見ると同一オリジンの API になり、CORS の設定が要らない。
- 検証: 各ゲームの Worker は ID 基盤の公開鍵で Cookie の署名を検証し、ID を取り出す。ゲームの API ごとに ID 基盤へ問い合わせない。Clerk の `authenticateRequest` をこの検証に置き換える。
- 引き継ぎ: 8 文字、有効 10 分、1 回限りのコードを発行し、別端末で入力すると、その端末の Cookie を発行元の ID に切り替える。入力は IP 単位で頻度を制限する。切り替え前にその端末が持っていた ID は、どの端末にも紐付かなくなる。記録を統合しない。
- 引き継ぎ用トークン: 引き継ぎコードとは別に、推測できない長さの乱数を、ID と結び付けて前もって登録できるようにする。ID 基盤はハッシュだけを保存し、有効期限までは同じトークンを複数の端末で使える。受け取ったときの動作は引き継ぎコードと同じ。既存の記録の移行に使う。ID 基盤は Clerk に依存しない。
- 復旧コード: 端末のデータを消したときに ID へ戻るための、推測できない長さの秘密の文字列。アカウント画面で発行し、一度だけ表示して利用者に控えてもらう。ID 基盤はハッシュだけを保存する。いつでも再発行でき、再発行すると古いコードは使えなくなる。入力すると、その端末の Cookie を復旧コードの ID に切り替える。入力は IP 単位で頻度を制限する。
- 名前: ID 基盤が名前と重複の判定を持つ。ゲームの Worker は名前の登録を ID 基盤へ依頼し、成功した名前を自分の D1（TAKO-SEN では `leaderboard_profiles`）へ写してランキングの結合に使う。別のゲームで名前を設定済みの ID には、名前を聞かずにそのゲームの公開への同意だけを求める。
- 退会: アカウント画面から実行する。ID 基盤は ID と名前を削除し、各ゲームの Worker に記録の削除を依頼する。削除済みの ID の Cookie を別端末が持ち続けても、記録を作り直せないようにする。
- 濫用への対策: ID の発行は IP 単位で頻度を制限する。状態を変える API は `Origin` が許可済みのホストと一致することを必須にする（Cookie 認証に変えると、他サイトからのリクエストにも Cookie が付くため）。
- オフライン: ID 基盤に届かない場合もゲームは止めない。発行は次の機会に再試行する。

`src/core` が持つローカルの匿名 `userId` は、従来どおりサーバーでの所有権の証明に使わない。所有権の証明に使うのは、ID 基盤が発行して署名した ID だけとする。

Cookie の形式、鍵の管理、API の一覧、D1 のスキーマは `kan/game` リポジトリの設計書に記す。本書には TAKO-SEN から見た契約だけを残す。

### TAKO-SEN 側の変更

- Worker: `src/worker/index.ts` の Clerk による認証を Cookie の署名検証に置き換える。`/api/id/*` の中継を追加する。`/api/clerk-webhook` と `DELETE /api/account` を廃止し、ID 基盤から呼ばれる記録削除の API を追加する。`account_id` 列の型と各テーブルのスキーマは変えず、値が新しい ID になる。
- 画面: `@clerk/vue` の `useAuth` と `SignInButton` を使う 6 つのコンポーネントを、ID の状態を返す自前の composable に置き換える。API の呼び出しは Bearer トークンから Cookie に変える。
- 記録の同期: 名前を設定する前のクリアも本人の履歴として受け付ける。`POST /api/plays` の `profile_required` による拒否をやめる。`saveCompletedPlay` は名前と同意がない記録を `ranking_eligible = 0` で保存するので、ランキングには出ない。名前のない ID からの登録にも頻度制限をかける（現在の制限はランキング対象の記録にしかかからない）。ID の発行前にオフラインでクリアした記録は送信しない。
- 初回スコアの判定: 名前を設定する前に解いた問題は、設定後に再びクリアしてもランキングに出さない。現在の `first_ranked_plays` はランキング対象の記録だけを数えるので、設定前のクリアがあっても設定後の最初のクリアを初回として公開してしまう。同じ ID と問題 ID の記録が先に 1 件でもあれば対象外にするよう、判定を変える。初回スコアだけを公開する理由（解いたことのある問題は有利になる）が、設定前に解いた問題にも当てはまるため。
- 送信の説明: 設定画面に、クリアの記録がこの端末の ID で保存されることと、名前を決めるまで公開されないことを 1〜2 行で書き、プライバシーポリシーへのリンクを置く。
- 設定の受け取り: 旧 URL から渡された設定を検証して端末に保存する（「既存の記録の移行」を参照）。
- 導線: 「ログイン」ボタンをなくす。デイリー、超級、共有リンクの作成、ランキングへの参加の前提は「ログイン済み」から「名前と同意を設定済み」に変わる。アカウントモーダルには引き継ぎコードの発行と入力を加え、ログアウトをなくし、退会はポータルのアカウント画面へ案内する。チュートリアルの最後の案内も同じ内容に直す。
- テスト: Clerk をモックしている UI テストと Worker テストを、新しい ID の検証に合わせて書き直す。`vitest.config.ts` のテスト用公開キーの固定は不要になる。
- 文書: `DESIGN.md`、`DATA_CONTRACT.md`、`README.md`、`DEPLOY_DEV.md` の認証に関する記述を更新し、本番の手順を `DEPLOY_PROD.md` として新設する。
- 環境: `wrangler.jsonc` に本番環境を追加し、Worker、D1、カスタムドメイン、`ALLOWED_ORIGINS` を開発環境と分ける。`main` からは Clerk の依存と 3 つの secrets を R2 で削除する。

第 2〜5 段階の記述のうち、次の 4 点を本節で置き換える。それ以外の仕様（初回スコアだけを公開、過去のローカル履歴を取り込まない、プレイ中の盤面を同期しない、未送信キューを ID ごとに分ける）は維持する。

1. 「認証は Clerk」→ 自前の匿名 ID。
2. 「未ログイン」という状態 → オンラインで開いた利用者は必ず ID を持つ。区別が残るのは「名前と同意を設定済みか」だけ。
3. 「退会で Clerk アカウントを削除」→ ID 基盤での一括退会。
4. 「名前と同意の設定前のクリアは送信しない」→ ID を持つ端末のクリアは設定前から本人の履歴として送信する。公開は設定後のクリアに限る。

### 既存の記録の移行

開発用 D1 の `account_id` は Clerk のユーザー ID になっている。データは切り替えの時点で本番へ移しておき、本人との結び付けだけを後から行う。本人の確認は旧 URL に残した Clerk で行い、本番には Clerk を持ち込まない。

1. Clerk のユーザー ID ごとに、新しい ID と引き継ぎ用トークン（推測できない長さの乱数）を 1 つずつ割り当てる。
2. 開発用 D1 を書き出し、`account_id` を新しい ID に置き換えて本番 D1 へ取り込む。ゲーム名と引き継ぎ用トークンのハッシュは ID 基盤へ登録し、同意の状態は TAKO-SEN の D1 に引き継ぐ。
3. 旧 URL の D1 に「Clerk のユーザー ID → 引き継ぎ用トークン」の表を置く。旧 URL は移転の案内と Clerk のログインだけを提供する。
4. 利用者が旧 URL で Clerk にログインすると、旧 URL の Worker が本人のトークンを返し、画面がトークンを付けて `tako.kan-game.app` の引き継ぎ画面へ移動する。
5. 本番の引き継ぎ画面は、切り替えの内容を表示して確認を求め、ID 基盤へトークンを送る。ID 基盤はその端末の Cookie をトークンに対応する ID へ切り替える。記録を統合しない。
6. 移行期間が終わったら、旧 URL の Worker を止め、Clerk のアプリケーションと未使用のトークンを削除する。

- トークンは URL のフラグメント（`#` 以降）に載せて渡し、本番の画面が同一オリジンの API へ POST する。フラグメントはサーバーへ送られず、アクセスログとリファラーに残らない。旧 URL から直接 POST する形にしないのは、状態を変える API に `Origin` の一致を必須とする規則へ例外を作らずに済ませるため。
- 確認画面を挟むのは、他人のトークン付きの URL を踏まされて、気付かないまま端末の ID を切り替えられることを防ぐため。
- 旧 URL だけで動くコードは、`main` と分けたブランチに置く。ブランチは R2 の着手時に切り、切り替えまでは現在の Clerk 版をそのまま旧 URL で動かす（修正が必要になればこのブランチで行う）。切り替え時に、同じブランチを移転の案内と引き継ぎだけの内容に入れ替える。`main` は R2 で Clerk を削除する。
- Clerk は現在の開発用インスタンスと現在のドメインのまま使うので、設定を変えない。
- 引き継ぎの前にその端末で遊んだ記録は、切り替え前の ID に残る。引き継ぎ画面でこのことを説明し、旧 URL の案内で引き継ぎを先に行うよう促す。
- 移行期間は本番公開から 3 か月とし、終了日を旧 URL の案内に書く。期間内に引き継がれなかった記録と名前は、ランキングにそのまま残す。削除すると、他の参加者の順位と、問題の採択に使う登録人数が変わるため。持ち主が引き継げなくなった名前は、ほかの人も取得できない。本人からの削除の依頼は運用で受ける。

端末のローカル保存は旧 URL のオリジンに残り、新 URL からは読めない。このうち設定だけを引き継ぐ。

- 引き継ぐもの: 自動×、難易度の選択、効果音、振動の設定と、チュートリアルの既読状態。旧 URL の画面が、新 URL へ移動するときに URL のフラグメントへ載せて渡す。Clerk にログインしない利用者にも渡す。
- 引き継がないもの: ローカル成績、プレイ中の盤面、未送信の記録。未送信の記録を減らすため、切り替えの前に旧 URL で告知する。
- 新 URL の画面は、受け取った値を既存の設定の読み込みと同じ規則で検証し、不正な値は捨てる。すでに新 URL で設定を変えている端末では上書きしない。

### vegtab を合流させるときの論点
