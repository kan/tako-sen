# 公開環境のクエリ性能調査

## 2026-10-11: 通常問題候補・ランキング

対象は公開 Worker `tako-sen` と D1 `tako-sen-dev`。調査開始時の完了履歴は2,225件、初回公開登録は2,192件、プロフィールは11件。難易度別完了履歴は初級51件、中級26件、上級2,148件。順位付け・公開同意・初回成績の仕様は変更しない。

### 原因と改善

- 次問題候補の本人完了済み除外は、各公開記録について本人履歴を再走査していた。
- 公開記録の難易度検索、本人の盤面検索、盤面別初回公開記録検索に必要な索引が不足していた。
- `0008_ranking_query_indexes.sql` で3本の索引を追加。公開記録や履歴の更新・削除はしない。
- 本人完了済み盤面と公開同意アカウントは `NOT IN` / `IN` の一覧として取得し、相関サブクエリと各記録ごとのプロフィール検索を避ける。盤面IDは `NOT NULL` のため `NOT IN` のNULL問題は起きない。
- 登録人数の多い盤面優先・同数時のランダム・最大30候補・本人の非公開履歴を含む完了済み除外を維持。

### 実測

最初の計測では上級候補SQLが863ms、延べ約298万行の読み取り。索引追加後は約3.4ms・約1.1万行。この計測には対象アカウントを選ぶ補助SQLも含まれ、API自体の走査数とは異なる。

追加比較では対象アカウントの取得を別処理に分け、同じ実アカウントを直接指定して3回実行した。索引追加直後のSQLは毎回9,021行・5.44〜5.62ms、一覧方式は毎回4,711行・2.86〜3.88ms。取得上限適用前の全候補について双方向 `EXCEPT` の差分0件を確認した。測定中にもプレイ記録が増えるため、別時点の数値を厳密な同条件比較とはしない。

ランキングSQLの代表盤面は8人。索引追加とJOIN条件の改善で4,438行・4.38msから82行・0.37msへ。公開APIの5回測定は改善前で約134〜261ms（ネットワーク等を含む）。SQL時間とAPI全体時間を混同しない。

`rows_read` は複数の表・索引への延べアクセス数で、実際の保存件数ではない。候補の人数集計・最多人数優先・ランダムな同数順位を維持するには、対象の公開記録の集計が必要。さらに大幅に減らすための集計テーブル・キャッシュは、退会・同意撤回・初回登録との整合性コストを伴うため今回は導入しない。

次の問題ではAPIの後にブラウザでシード再生成・検証も行う。参考として開発機の単一seedで生成約161〜760ms、盤面ID検証約1〜2msを確認したが、端末・seedによって変わる。今回Generatorや旧シードの再現性は変更しない。

[D1の索引・実行計画・読み取り行数の公式説明](https://developers.cloudflare.com/d1/best-practices/use-indexes/)に沿って確認。

### 追加改善: 初回公開判定の重複JOINを除去

`publish_first_clear` トリガーは初回登録に一致した行だけ `is_public = 1` にする。取得時の `first_ranked_plays` JOINはこの判定を繰り返していたため、通常候補・ランキングの読み取りは公開フラグを使用する。書き込み側の初回登録テーブル・トリガーは維持し、現在の公開同意の確認も残す。公開DBで「初回登録に一致しない公開行」「同一アカウント・盤面の重複公開」はともに0件だった。

全3難易度について、履歴1,171件の利用者・32件の利用者・履歴なしの3条件で、取得上限前の全候補を双方向 `EXCEPT` 比較し差分0件。代表的な読み取り行数は以下（同時点の新旧比較）。

## 2026-10-11: 盤面生成、次の問題の先読み、超級の進捗取得

前節までの対応で SQL は 1 回あたり数 ms 以下になった。残る重さを調べた結果、原因は SQL ではなく次の 2 つだった。リモートの D1 には問い合わせず、全マイグレーションを適用した一時的な SQLite と開発機での実行時間で確認した。

- 「次の問題」の待ちの大半は、ブラウザでの盤面の再生成だった。生成はメインスレッドで同期実行され、その間は画面が止まる。
- ログイン中の端末は、30 秒ごとに `GET /api/super/progress` を無条件で呼んでいた。1 回につき認証と D1 への 4 往復が発生する。

### 盤面生成の高速化

生成される盤面は問題 ID の元になるので、出力を変えずに速くした。乱数の消費順と探索順は変えていない。

- 唯一解の判定（`solvePuzzle`）は、`Set` と座標オブジェクトの生成をやめて配列で判定する。隣接の判定は直前の行のタコだけを見る。行ごとに 1 匹ずつ順に置くので、触れ得るのは直前の行のタコに限られる。
- 難易度の判定（`analyzePuzzleDifficulty`）は、1 手ごとに全定石の手を列挙してから最も易しい手を選んでいた。優先度の低い定石から順に探し、手が見つかった段階で打ち切る。複数 Region の Line 消去と Region 枯渇の探索は、易しい手がない時だけ走る。

開発機で seed 12 件ずつを生成した時間は次のとおり。変更の前後で、36 件すべての Region、正解、初期配置、評価、手数が一致した。

| 難易度 | 変更前の中央値 | 変更後の中央値 | 変更前の最大 | 変更後の最大 |
| ------ | -------------: | -------------: | -----------: | -----------: |
| 初級   |         198 ms |          82 ms |       522 ms |       236 ms |
| 中級   |         450 ms |         112 ms |     1,794 ms |       463 ms |
| 上級   |         359 ms |          95 ms |     1,711 ms |       326 ms |

`tests/solver-analysis-equivalence.test.ts` が、変更前の定義をそのまま残した参照実装と結果を比べる。固定ハッシュによる `g1`、`g2`、`daily-v1`、`super-v1` の回帰テストも変更なしで通る。10×10 のデイリーと超級も同じソルバと判定を使うので速くなる。モバイル端末での時間は計測していない。

### 次の問題の先読みと Web Worker での生成

- 盤面の生成を Web Worker（`src/ui/puzzle-worker.ts`）で行い、生成中も画面を止めない。Worker を使えない環境と、Worker が失敗した後は、従来どおりメインスレッドで生成する。
- 通常プレイで盤面に最初の手を入れてから 2 秒後に、次の問題の候補取得と再生成を済ませておく。「次の問題へ」ではその結果を使う。この起動中に盤面へ手を入れていない試行では先読みしない。保存済みの盤面を開いただけで離れる場合に API を呼ばないため。
- 用意した時点から試行、難易度の選択、アカウントのどれかが変わったら、用意した結果を捨て、進行中の候補取得と生成を中断する。実行中の生成は途中で止められないので、Worker を作り直し、まだ必要な要求だけを渡し直す。
- 先読みで候補を取得できなかった場合（通信の失敗、タイムアウト、セッションの未取得）は、結果を残さない。「次の問題へ」を押した時に候補を取り直すので、一時的な失敗で候補のある問題を逃さない。
- Worker が 10 秒応答しない場合と、Worker での生成が失敗した場合は、メインスレッドでの生成に切り替える。「次の問題へ」が進まなくなることを防ぐ。
- 先読みは Worker を使える時だけ行う。メインスレッドで生成するとプレイ中の入力が止まるため。
- 候補の選び方、問題 ID の照合、通信できない時にクライアント生成へ戻る動作は変えていない。`GET /api/next-puzzle` の呼び出しは、これまでの「次の問題へ」を押した時から、最初の手の 2 秒後へ移る。

### 超級の進捗取得の削減

- 30 秒ごとの同期は、未送信の記録の再送だけを行う。送るものが無ければ通信しない。進捗の再取得は、次のどれかに当てはまる時だけ行う。
  - 今回の同期で記録を送信した。
  - 前回の同期が失敗した。
  - このアカウントの進捗をまだ取得していない。
- 画面へ戻った時（フォーカス、タブの再表示）は、最後の取得から 30 秒以上たっていれば取得する。起動時、通常問題のクリアの同期後、オンライン復帰時の取得は従来どおり。
- この結果、画面を開いたまま操作していない端末は、他の端末で増えた回数や挑戦権を、次に画面へ戻るかクリアするまで表示しない。サーバーが正本であることと、開始時にサーバーで権利を確認することは変わらない。
- サーバー側は、進捗の行の作成と読み取りを 1 回の `batch` にまとめた。進捗の行を扱う API（`progress`、`event`、`defer`、`prepare`、`start`）は、進捗の行を読むたびに現在の同意を確認するので、ルーターでのプロフィールの確認を省いた。それ以外の超級の API は、従来どおりルーターで確認する。`GET /api/super/progress` は D1 への 4 往復から 1 往復になり、`event` と `defer` は 3 往復、`prepare` と `start` は 2 往復減る。同意のないアカウントへの `403 profile_required` は変わらない。ただしこの 4 つでは、同意がなく本文も不正な要求への応答が `403` から `400` または `415` に変わる。

### 超級の索引

`0011_super_query_indexes.sql` で索引を 2 本追加した。データは変更しない。

- `super_first_scores (puzzle_id, account_id, play_id)`: 主キーが `account_id` から始まるので、盤面を指定したランキングの取得が全プロフィールを走査していた。`0008` で通常問題の `first_ranked_plays` に足した索引と同じ理由。
- `super_attempts (account_id, puzzle_id)`（完了済みだけの部分索引）: 候補の取得で、本人が完了した盤面を除く判定に使う。

現在の件数では差を測れない。現在の 100 倍を模した合成データでは、ランキングが 8.3 ms から 1.5 ms、候補が 145 ms から 49 ms になった。実行計画が 2 本の索引を使うことは `tests/super-worker.test.ts` で確認する。

開発サーバーをヘッドレスの Chromium で開き、未ログインの状態で確認した。

- 盤面に手を入れる前は、生成用の Worker が起動しない。
- 最初の × から 3 秒後には Worker が 1 つ起動している。

ログイン中の候補取得を含む経路と、モバイル端末での動作は確認していない。

### クリア時のランキング取得

上記のデプロイ後、利用者から、クリア時のランキング表示にまだ体感できる遅れがあるとの指摘があった。ログイン中に通常問題をクリアすると、通信が 3 回続いていた。

1. クリアダイアログが開いた時点でランキングを取得する。
2. クリアの記録を送信する（`POST /api/plays`）。
3. 送信が終わると、ランキングをもう一度取得する。

1 の応答には自分の記録がまだ載っていない。ダイアログは自分の前後 3 件だけを表示するので、1 の結果は表示に使えず、自分の順位が出るのは 3 の後だった。取得中の表示も 2 回出ていた。次のように変えた。

- 記録の送信の応答に、その問題のランキングを含める。画面はそれを表示し、3 の取得をしない。
- 記録を送信している間は 1 の取得をせず、取得中の表示のまま待つ。待つのはダイアログを開いた時の 1 回だけで、3 秒たっても送信が終わらなければ、待つのをやめて取得する。送信が後から終われば、応答のランキングに置き換える。
- 表示した後に走る再送（30 秒ごとの再試行など）では、表示を消さず、取得もしない。
- 送信に失敗した時と、応答にランキングがない時は、従来どおり 1 回だけ取得する。
- `POST /api/plays` は、プロフィールを読み終えてから本文の読み取りと記録の検証を始めていた。プロフィールの読み取りを先に始め、その間に検証を進める。どの応答を返す前にも読み取りの結果を待つので、同意のないアカウントへの `403 profile_required` は、本文が不正な場合と登録済みの記録の再送を含めて変わらない。

自分の順位が出るまでの通信は 3 回から 1 回になる。その 1 回の中で、D1 への往復は 1 回増える（ランキングの読み取り）。プロフィールの読み取りは検証と重なる分だけ短くなる。時間は実測していない。未ログインの場合と、名前を設定していない場合は記録の送信がないので、動作は変わらない。

### 見送ったこと

- Clerk の鍵取得をなくす対応は行わない。本番リリースで Clerk を使わなくなるため。置き換え後の検証鍵は環境変数に埋め込み、読み込みを 1 回にする（`NEXT_PHASE.md`「本番リリース計画」）。
- 公開ランキングの短時間キャッシュ、週間ランキングの絞り込みの前倒し、候補の人数集計の事前計算は今回行っていない。
- クリア時に端末で順位を計算して即表示する案は採らなかった。順位付けの規則を端末にも持つことになり、サーバーの順位と食い違うおそれがあるため。デプロイ後の実機確認で遅れはまだ残ったが、利用者はこの副作用を踏まえ、現状を採用すると判断した（2026-10-11）。件数が現在の 10 倍になるまでは SQL の時間は問題にならない見込み。
