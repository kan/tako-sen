# 公開環境のクエリ性能調査

## 2026-10-11: 通常問題候補・ランキング

対象は公開 Worker `tako-sen` と D1 `tako-sen-dev`。調査開始時の完了履歴は2,225件、初回公開登録は2,192件、プロフィールは11件。難易度別完了履歴は初級51件、中級26件、上級2,148件。順位付け・公開同意・初回成績の仕様は変更しない。

### 原因と改善

- 次問題候補の本人完了済み除外は、各公開記録について本人履歴を再走査していた。
- 公開記録の難易度検索、本人の盤面検索、盤面別初回公開記録検索に必要な索引が不足していた。
- `0008_ranking_query_indexes.sql` で3本の索引を追加。公開記録や履歴の更新・削除はしない。
- 本人完了済み盤面と公開同意アカウントは `NOT IN` / `IN` の一覧として取得し、相関サブクエリと各記録ごとのプロフィール検索を避ける。盤面IDは `NOT NULL` のため `NOT IN` のNULL問題は起きない。
- 登録人数の多い盤面優先・同数時のランダム・最大30候補・本人の非公開履歴を含む完了済み除外を維持。

### 実測

最初の計測では上級候補SQLが863ms、延べ約298万行の読み取り。索引追加後は約3.4ms・約1.1万行。この計測には対象アカウントを選ぶ補助SQLも含まれ、API自体の走査数とは異なる。

追加比較では対象アカウントの取得を別処理に分け、同じ実アカウントを直接指定して3回実行した。索引追加直後のSQLは毎回9,021行・5.44〜5.62ms、一覧方式は毎回4,711行・2.86〜3.88ms。取得上限適用前の全候補について双方向 `EXCEPT` の差分0件を確認した。測定中にもプレイ記録が増えるため、別時点の数値を厳密な同条件比較とはしない。

ランキングSQLの代表盤面は8人。索引追加とJOIN条件の改善で4,438行・4.38msから82行・0.37msへ。公開APIの5回測定は改善前で約134〜261ms（ネットワーク等を含む）。SQL時間とAPI全体時間を混同しない。

`rows_read` は複数の表・索引への延べアクセス数で、実際の保存件数ではない。候補の人数集計・最多人数優先・ランダムな同数順位を維持するには、対象の公開記録の集計が必要。さらに大幅に減らすための集計テーブル・キャッシュは、退会・同意撤回・初回登録との整合性コストを伴うため今回は導入しない。

次の問題ではAPIの後にブラウザでシード再生成・検証も行う。参考として開発機の単一seedで生成約161〜760ms、盤面ID検証約1〜2msを確認したが、端末・seedによって変わる。今回Generatorや旧シードの再現性は変更しない。

[D1の索引・実行計画・読み取り行数の公式説明](https://developers.cloudflare.com/d1/best-practices/use-indexes/)に沿って確認。

### 追加改善: 初回公開判定の重複JOINを除去

`publish_first_clear` トリガーは初回登録に一致した行だけ `is_public = 1` にする。取得時の `first_ranked_plays` JOINはこの判定を繰り返していたため、通常候補・ランキングの読み取りは公開フラグを使用する。書き込み側の初回登録テーブル・トリガーは維持し、現在の公開同意の確認も残す。公開DBで「初回登録に一致しない公開行」「同一アカウント・盤面の重複公開」はともに0件だった。

全3難易度について、履歴1,171件の利用者・32件の利用者・履歴なしの3条件で、取得上限前の全候補を双方向 `EXCEPT` 比較し差分0件。代表的な読み取り行数は以下（同時点の新旧比較）。

| 1,171件    | 初級   |   3,870 |      1,346 |
| 1,171件    | 中級   |   3,826 |      1,297 |
| 1,171件    | 上級   |   4,723 |      4,088 |
| 32件       | 中級   |   4,379 |         87 |

前回SQLは実行計画が初回登録テーブルを起点にしており、初級・中級でも別難易度の初回登録を調べていた。JOIN除去後は難易度の公開部分索引から直接絞り込む。ランキングも代表8人の盤面で83行から67行になり、表示内容は一致した。

さらに本人の履歴一覧の読み取りも避けるため、複合索引による `NOT EXISTS` の一点検索を採用した。当初の遅い相関検索と異なり `(account_id, puzzle_id)` の両方を索引で指定する。初級・中級を選んでも、本人の大量の上級履歴を丸ごと読む必要がなくなる。

履歴多数・上級だけは一覧方式より約11%増えるが、それでも前回公開SQLの読み取りより少なく、他の8条件で減る。利用者別の複雑な分岐や追加カウントクエリは導入しない。

GROUP BY順の索引追加も合成データで試したが、追加索引の容量・書き込みコストが増えるため採用しなかった。今回の変更はスキーマ変更なし。

公開フラグの意味を将来変更する場合は、候補・ランキング双方を再検討すること。再挑戦の人数重複、同意前履歴の非公開維持、同意撤回、退会、初回スコア保持はテストで保証する。

最終SQLを前回公開SQLと直接比較した追加検証でも、3難易度×3利用状況の全9条件で双方向 `EXCEPT` の差分0件を確認。履歴1,171件の利用者で初級3,880→135行、中級3,833→98行、上級4,730→4,566行。履歴32件の上級では12,083→5,730行、履歴なしの上級では12,313→5,739行。ランキングは83→67行、8人の表示内容・順位は一致した。SQL実行時間は最終候補で約0.22〜3.33ms。読み取り行数は利用者の履歴と難易度に依存するため、特定利用者の数値を全利用者共通とは扱わない。
